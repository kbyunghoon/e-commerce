# 카프카 구조 및 동작 정리

## 1. Apache Kafka 개요

### 카프카의 정의 및 특징
Apache Kafka는 링크드인에서 개발된 분산형 스트리밍 플랫폼으로, 실시간 데이터 스트림을 처리하기 위한 오픈소스 **메시지 브로커**다.

#### 주요 특징
- **고처리량**: 초당 수백만 건의 메시지 처리 가능
- **고가용성**: 브로커 장애 시에도 서비스 지속 가능
- **비동기 처리**: Producer와 Consumer가 독립적으로 동작
- **분산 시스템**: 여러 서버에 분산되어 확장성 제공
- **내구성**: 디스크에 메시지를 영구 저장
- **순서 보장**: 파티션 내에서 메시지 순서 보장
- **확장성**: 필요에 따라 브로커 및 파티션 추가 가능

### 왜 대용량 시스템에서 Kafka를 사용하는가?

1. **대용량 데이터 처리**: [초당 수백만 건의 메시지를 안정적으로 처리](#4--kafka가-고성능안정성을-보장하는-이유)
2. **시스템 간 분리**: Producer와 Consumer의 독립적 운영으로 시스템 결합도 감소
3. **장애 복구**: 브로커 장애 시 자동 페일오버로 서비스 연속성 보장
4. **확장성**: 수평 확장을 통한 처리량 증대
5. **실시간 처리**: 낮은 지연시간으로 실시간 데이터 처리 지원
6. **데이터 재처리**: 메시지 보관을 통한 과거 데이터 재처리 가능

## 2. Kafka의 구성 요소 이해

### Broker
- **정의**: Kafka 서버 인스턴스
- **역할**: 메시지를 저장하고 클라이언트 요청을 처리
- **특징**:
  - 클러스터는 여러 브로커로 구성
  - 각 브로커는 고유한 ID를 가짐
  - 하나 이상의 토픽 파티션을 담당
  - 클라이언트 연결을 관리하고 메타데이터 제공

#### 클러스터 (Cluster)
- **정의**: 여러 브로커들의 집합
- **역할**: 분산 처리와 고가용성 제공
- **관리**: 주키퍼(Zookeeper) 또는 KRaft로 관리

### Topic & Partition

#### 토픽 (Topic)
- **정의**: 메시지를 구분하는 논리적 단위
- **역할**: 메시지의 카테고리나 피드 이름
- **구성**: 여러 파티션으로 구성됨
- **예시**: `user-events`, `payment-logs`, `order-notifications`

#### 파티션 (Partition)
- **정의**: 토픽을 물리적으로 분할한 단위
- **특징**:
  - 순서가 보장되는 불변의 로그 구조
  - 각 파티션 내에서만 순서 보장
  - 파티션 번호는 0부터 시작
  - 병렬 처리와 확장성을 제공
- **오프셋 (Offset)**:
  - 파티션 내 메시지의 고유한 식별자
  - 순차적으로 증가하는 숫자
  - Consumer가 어디까지 읽었는지 추적하는 용도

#### 복제 (Replication)
- **정의**: 파티션의 복사본을 여러 브로커에 저장
- **구조**: 리더(Leader)와 팔로워(Follower)로 구성
- **설정**: 복제 팩터(Replication Factor)로 복제본 개수 결정

### Producer / Consumer

#### 프로듀서 (Producer)
- **정의**: 메시지를 토픽으로 전송하는 클라이언트
- **역할**:
  - 메시지 생성 및 전송
  - 파티션 배정 전략 결정 (Round-robin, Key-based 등)
  - 배치 처리를 통한 성능 최적화
- **특징**:
  - 비동기 전송 지원
  - 전송 실패 시 재시도 기능
  - 압축 옵션 제공

#### 컨슈머 (Consumer)
- **정의**: 토픽에서 메시지를 읽어오는 클라이언트
- **역할**:
  - 메시지 소비 및 처리
  - 오프셋 관리
  - 컨슈머 그룹 단위로 동작

#### 컨슈머 그룹 (Consumer Group)
- **정의**: 하나 이상의 컨슈머로 구성된 논리적 그룹
- **특징**:
  - 같은 그룹 내 컨슈머들은 파티션을 분담하여 처리
  - 장애 발생 시 리밸런싱 수행
  - 확장성과 가용성 제공

### 기타 핵심 개념

#### 메시지 (Message)
- **정의**: Kafka에서 전송되는 데이터의 기본 단위
- **구조**: Key-Value 형태로 구성 (Key는 선택사항)
- **특성**: 불변성(Immutable) 특성을 가짐

## 3. 데이터 흐름
- Producer → Topic → Partition → Consumer

### 전체 데이터 흐름 개요
```text
Producer → Kafka Broker → Topic → Partition → Consumer Group → Consumer
```

#### 1단계: Producer → Kafka Broker
- 메시지 생성: Producer가 전송할 메시지를 생성
- 직렬화: 메시지를 바이트 배열로 변환
- 파티셔닝: 메시지를 어느 파티션으로 보낼지 결정
  - Key 기반: 동일한 Key는 같은 파티션으로 
  - Round-robin: Key가 없을 때 순환 배정 
  - 사용자 정의: Custom Partitioner 사용
- 배치 처리: 성능 최적화를 위해 메시지를 배치로 묶음
- 전송: 해당 파티션의 리더 브로커로 전송

#### 2단계: Kafka Broker → Topic → Partition
- 메시지 수신: 브로커가 Producer로부터 메시지를 받음 
- 검증: 메시지 형식과 권한 확인 
- 저장: 지정된 토픽의 파티션에 메시지를 추가 (append-only)
- 오프셋 할당: 파티션 내에서 고유한 오프셋 번호 부여 
- 복제: 팔로워 브로커들에게 복제본 전송 
- 응답: Producer에게 성공/실패 응답

#### Step 3: Partition → Consumer Group → Consumer
1. 구독: Consumer가 특정 토픽을 구독
2. 파티션 할당: 컨슈머 그룹 내에서 파티션 분배
   - 각 파티션은 그룹 내 하나의 컨슈머에게만 할당
   - 컨슈머 수 변경시 리밸런싱 발생
3. 폴링: Consumer가 할당된 파티션에서 메시지를 가져옴
4. 역직렬화: 바이트 배열을 원래 객체로 변환
5. 처리: 비즈니스 로직 수행
6. 오프셋 커밋: 처리 완료된 메시지의 오프셋을 저장

### 데이터 흐름 특징
#### 순서 보장
- 파티션 내에서만 순서가 보장됨
- 토픽 전체적으로는 순서 보장되지 않음
- 순서가 중요한 경우 단일 파티션 사용 고려

#### 중복 방지와 정확히 한 번 처리
- At-least-once: 최소 한 번 전달 (중복 가능)
- At-most-once: 최대 한 번 전달 (손실 가능)
- Exactly-once: 정확히 한 번 처리 (Kafka 0.11.0+)

## 4. ✅ Kafka가 고성능·안정성을 보장하는 이유
### 디스크 기반 Sequential Write (로그 구조 저장소)
- 일반 DB는 랜덤 I/O가 많지만, Kafka는 메시지를 디스크에 순차적으로 append한다.
- HDD/SSD 모두 순차 쓰기 성능이 랜덤 쓰기보다 훨씬 빠르기 때문에 고속 처리 가능하다.
- 운영체제의 페이지 캐시(Page Cache)를 활용하여 디스크 I/O를 최소화해준다.

### Zero-Copy 전송 (파일 → 네트워크 직접 전송)
- 메시지를 읽어 전송할 때 Kafka는 애플리케이션 레벨에서 데이터를 다시 복사하지 않고,
  커널의 `sendfile()` 시스템 콜을 사용해 디스크에서 네트워크 소켓으로 직접 전달한다.
- CPU 오버헤드가 줄어들어 처리량이 매우 높아진다.

### 분산 아키텍처 (Partition + Broker)
- 토픽을 여러 개의 파티션으로 나누어 병렬 처리한다.
- 여러 Broker(서버)에 분산 저장되므로 확장성 확보가 가능하다.

### Batching & 압축 (효율적인 네트워크 사용)
- 메시지를 한 건씩 전송하지 않고 Batch 단위로 묶어 전송한다.
- 네트워크 오버헤드 감소한다.
- GZIP 같은 압축 지원 → 네트워크 사용량 절감 → 처리 속도 증가

### Replication 기반 안정성 보장
- 각 파티션은 여러 Broker에 복제된다.
- Leader Broker 장애 발생 시 Follower가 자동으로 Leader로 승격되어 데이터 유실 방지할 수 있다.
- ack 설정(acks=all 등)을 통해 원하는 수준의 내구성(durability) 확보 가능.
  - Kafka 3.0 이상부터 `acks=all`이 기본 값이다.

### Pull 기반 소비 모델
- Consumer가 Broker에서 스스로 가져가는 방식(pull)이기 때문에 처리 가능한 속도만큼 메시지를 가져올 수 있다.
  - → 과부하 방지, 안정성 ↑
